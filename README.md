# Agent 工作流 SOP · 直派 + 砍 AI 互请

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

> **姊妹项目**：[**wb-bot**](https://github.com/WinterMK-byte/wb-bot) —— 那是**机制层**（总线怎么写、通知怎么送达、资源怎么不打架、**会话怎么迁移**）。
> **本件是流程层**：决定「**活怎么派下去、谁该干什么**」。
> 两个配套使用；也可以单独看这一份。
>
> ★ **本 SOP 必须包含「迁移」**（§六）—— 因为执行层**会被不断重建**。
> 描述协作架构却不写迁移，等于漏掉一个**必然发生的运行事实**。

---

## 一句话

> **架构唯一的意义 = 省人的注意力。**
> **分层本身不值钱；「上下文 / 状态 / 工具的分工」才值钱。**

---

## 背景：为什么会需要这份 SOP

多席位架构用久了会退化成一种病：

> **「一个 AI 给另一个 AI 出主意 + 颠来倒去请示下发」**

而 **AI 之间能力没有差异** —— 向上请示的效果 ≈ 自己琢磨。**这是零和的**：
两边都烧了 token，产出却没有增加，只是把同一个犹豫传导了一遍。

这份 SOP 就是给这个病开刀。

---

## 一、四条核心原则

| # | 原则 | 说明 |
|---|---|---|
| **1** | **砍掉 AI 互请** | 同级之间不互相出主意、不请示「方案行不行」。拿到清晰目标 + 上下文，**直接干到底**，交付事实产物 |
| **2** | **路由看上下文匹配，不看级别** | 谁最贴（谁的上下文 + 工具最匹配）就给谁 —— **不是谁官大** |
| **3** | **总线降为事实流水账，不是审批流** | 只记「做了啥 / 产物在哪 / 下一步要啥事实」，供接续，**不等批准** |
| **4** | **人是唯一价值裁决者** | Agent 之间只传**事实 / 中间产物**，不传「判断请示」。该不该做 / 哪个方案好 / 优先级 = **人拍板** |

## 二、角色重定义

| 角色 | 新定位 | 干什么 |
|---|---|---|
| **人**（你） | 唯一方向 + 价值判断裁决者 | 给方向、拍板、价值判断 |
| **战略层** | 外脑 + **直派调度** | 读全貌 → 引导方向 → 写施工单 → **直派执行层**；不跟其他 Agent 商量 |
| **参谋**（每条业务线） | **稳定锚 + 强模型通道** | 不迁移（抗运行时脆弱性）+ 可上强模型做重活（低频）；业务线的稳定载体 |
| **执行层** | 长任务 / 系统 / 常驻 | 执行、跑腿、状态、定时 —— **★ 且会被不断重建**（见 §六） |
| **架构维护者** | **退为维护者** | 仅在席位 / 总线 / **迁移**机制变更时动；**不再是被请示的管理层** |

> ★ **关键修正**：参谋**不可替代**。
> 它的价值 = **稳定**（不迁移）+ **强模型通道**（贵但强、低频）——
> **不是「谁更聪明」**。保留参谋，但**摘掉「被请示」的帽子**。
>
> ★ **「不迁移」是参谋的定位，不是全员事实**：执行层**一定会**被重建（§六）。
> 一个只描述「谁不迁移」、不描述「谁迁移时怎么办」的架构，是不完整的。

**真杠杆在哪**：常驻执行方（状态 / 数据库 / 定时 / 长任务）、各业务线（专业上下文 + skill + 评测集）。
把**状态与工具**的杠杆用足，**别造层级**。

## 三、任务下发机制（施工单）

```
触发  人发出「去办 X」，或战略层判断需要派
  │
写单  目标 / 必要上下文路径 / 完成判据 / 路由（派给谁）/ 交付物位置
  │
投递  ① 集中收件箱（按责任方分子目录）
     ② ★ 贴脸放进接收方自己的工作区  ← 缺这条等于没投
  │
执行  目标会话读单 → 干到底
  │
回执  在总线记「完成 + 产物路径」—— 这是**事实**，不是请示
  │
回读  战略层读回执 → 给人下一轮引导
```

**一张单子最少要有**：目标 · 上下文路径 · 完成判据 · 路由 · 交付物位置。
（完整十项见 [wb-bot 的 docs/12](https://github.com/WinterMK-byte/wb-bot/blob/main/docs/12-handoff-discipline.md)）

## 四、最高效工作流

```
人（唯一拍板：方向 / 价值判断）
   │
   ▼
战略层 = 外脑 + 直派调度
   │  读全貌 → 引导方向 → 写施工单（目标 + 上下文 + 判据）
   │  直达，不经中间层，不跟别的 Agent 互请
   ▼
执行层（按上下文匹配直派）
   ├ 常驻执行方：长任务 / 系统 / 定时
   ├ 业务线 A（参谋 + 执行）：专业上下文
   ├ 业务线 B（参谋 + 执行）：专业上下文
   └ 侦查线：外部情报
   │  干到底 → 交付 → 记总线（事实）
   ▼
战略层回读 → 给人下一轮引导
```

> **别忘了 §六**：执行层会被**不断重建**。派单时为什么必须写清「上下文路径」——
> 就是为了**重建之后还能接上**。一张单只写「去办 X」，重建一次就断了。

## 五、总线用法变更

| | 旧 | 新 |
|---|---|---|
| 写什么 | 长条目**请示 / 批复** | 「做了啥 / 产物在哪 / 下一步要啥事实」 |
| 目的 | 等批准 | **供接续，不等批准** |
| 纪律 | 编号唯一、插在唯一位置 | **保持不变** |

> 一句话：**回执是事实登记，不是审批流。**
> 只有"需要人做价值判断"时才停下来请示 —— "我做完了"永远不需要请示。

## 六、迁移架构（**协作架构缺了它 = 残缺**）

> ★ **这一节是补进去的。**
> 本 SOP 初版描述了「谁该干什么」，却漏掉一个**必然发生的运行事实**：
> **执行层会被不断重建。**
> 漏了它，第一次重建就会**丢掉身份与在办事项** —— 而且**不会报错**。

### 6.1 为什么执行层必然被重建

| 触发 | 典型信号 |
|---|---|
| 上下文塞满 | 开始忘事、重复问已经答过的问题 |
| 模型换代 | 强模型只留给规划，日常执行要降本 |
| 机器重装 / 换机 | 系统迁移、盘迁移 |
| 进程崩了 | 依赖升级、端口被占、数据库损坏 |

⇒ **执行层是耗材：生命周期短于它承担的工作。**
「会话」是**壳**，「职责 + 在办事项」才是**本体** —— 把本体搬进新壳，这件事叫**迁移**。

### 6.2 所以 SOP 必须写迁移（三条理由）

1. **不写 = 描述了一个不存在的稳态。** 世界上没有「一条会话永远活着」的执行层。
2. **不写 = 丢的东西不会报错。** 新会话启动得很正常，只是从零开始 ——
   于是「同一件事做两遍」或「没人接着做」。
3. **不写 = 责任悬空。** 谁负责迁移？答案在 §二是「架构维护者」，
   但当时只写了席位与总线机制 —— **迁移必须一并写进去**。

### 6.3 接续必须带三样

按**丢失后果**排序：

| # | 带什么 | 丢了会怎样 |
|---|---|---|
| 1 | **身份块**（我是谁 / 职责 / 边界） | 开始干不属于自己的活；越界没人知道 |
| 2 | **在办事实**（最近 N 条流水） | 同一件事做两遍，或没人接着做 |
| 3 | **未闭口清单**（状态非「完成」的） | 「做了一半」那部分**彻底消失** —— 它是静默的 |

> ★ **第 3 样最容易丢**：已完成的条目躺在流水里，一眼能看到成果；
> **未完成的沉在中间，谁也不会主动去捞** —— 而它恰恰是唯一需要被接手的东西。

### 6.4 迁移之后必须查什么

路径写死后搬家，会引发一类**不报错的故障**：
读一个不存在的文件通常**不抛异常**，返回**空**；而空结果被读成「今天没事」。

⇒ 搬完必须扫一遍「还有谁指着旧位置」，**跑到零命中才算收口**。
（它比崩溃危险 —— 崩溃至少有人知道。）

### 6.5 谁来做、用什么做

| 事 | 归谁 | 怎么做 |
|---|---|---|
| 定「迁移必须带三样」这条规矩 | **架构维护者** | 本节 |
| 实际搬（生成接续文本） | **执行方自己**（重建前跑一次） | `wbb migrate render` |
| 搬完扫旧引用 | **执行方** | `wbb migrate audit` —— 零命中才算完 |
| 新会话认领未闭口 | **新执行方** | 逐条认领；不认领的写明「我不接」 |

> **机制层的可运行实现在姊妹项目 wb-bot**
> （[`docs/14-runtime-migration.md`](https://github.com/WinterMK-byte/wb-bot/blob/main/docs/14-runtime-migration.md)
> ＋ [`wbb/migrate.py`](https://github.com/WinterMK-byte/wb-bot/blob/main/wbb/migrate.py)）。
> **本 SOP 只负责把这条规矩定下来**：谁做、什么时候做、必须带什么。

### 6.6 ★ 迁移四律 —— 为什么迁移**老是搞错**

§6.1–6.5 讲的是「**怎么做**」。但只写「怎么做」**防不住反复出错** ——
本 SOP 自己就是例子：**0.3 才把迁移补进来**，说明**漏掉迁移是一件会发生的事**。

#### 先分清两类东西

| | **不变的（骨架）** | **会变的（指针）** |
|---|---|---|
| 是什么 | 规则 / 顺序 / 义务 —— 换个执行方**照样成立** | 实参：路径、会话 ID、谁在几号工作区、在办什么 |
| 例子 | 「开工先读身份块」「收尾必须登记总线」 | 某个目录名、某台机器的绝对路径、「今天在办 X」 |
| 生命周期 | 几乎不改 | **每重建一次就变一次** |
| 该放哪 | 主文档（**可以传很多代**） | **单独一份指针**，主文档只**引用**它 |
| 写死会怎样 | 无所谓 | ★ **静默漂移**：还指着上一代，读的人读了个空，**不报错** |

> ★ **一句话判据**：写下一个「**路径 / 编号 / 数量**」之前，先问
> —— **「它会不会变？谁在变它？」** 会变 → 不许进骨架，去指针里登记。

#### 四条律（前三条**机械可查**，第四条靠 review）

| # | 律 | 一句话 | 反例 |
|---|---|---|---|
| **一** | **会变的，不写死** | 骨架里不许出现实例形状（时间戳目录 / 机器绝对路径） | 席位总表里写死某个工作区目录 |
| **二** | **权威，只有一处** | 每样事实**只在一处**权威，别处只能**引用** | 总表一份、记忆里又抄一份，改一处另一处漂 |
| **三** | **入口，挂启动必读位** | **落地 ≠ 送达**；要挂到接收方**启动时真的会读到**的位置 | 改了机制，没改那个每次启动都读的入口 |
| **四** | **形状与接线，必须分离** | 可复用的**形状**（规矩）进文档/仓库，某台机器的**具体接线**留本机 | 把某台机器的路径混进通用流程 |

#### 四起同形事故（都真实发生过）

| 事故 | 当时以为 | 实际 | 对应律 |
|---|---|---|---|
| 迁移能力**没写进机制** | 「做完了」 | 机制在，但**没人读得到** | 律三 |
| 任务里**写死绝对路径** | 「配置好了」 | 搬家后每天**读空**，被当成「今天没事」 | 律一 |
| **本 SOP 0.1–0.2 漏了迁移整节** | 「文档挺全」 | 描述了「谁干什么」，没说「**换壳后还该干什么**」 | 律四 |
| 席位总表**把自己钉在旧工作区** | 「表填好了」 | 下一代**认不出自己** | 律一 / 律二 |

⇒ **共同形状**：`路径被写死` / `权威有两份` / `入口没挂` / `形状与接线混着`。
⇒ **结论**：**靠「记得」防不住，靠「判据」才防得住。**

#### 怎么落地

| 做什么 | 用什么 |
|---|---|
| **定规矩**（本节） | 本 SOP |
| **机械查**（前三条） | wb-bot 的 [`tools/migrate_check.py`](https://github.com/WinterMK-byte/wb-bot/blob/main/tools/migrate_check.py) —— 接进 CI |
| **防本 SOP 自己再漏这一节** | 本仓库 `tools/docs_check.py` 的「**迁移架构不得漏**」检查（缺任一判据词即失败） |

> ★ 最后一条是**自我约束**：一份写了「迁移不得漏」的文档，
> **必须自己也受这条检查管** —— 否则它只是又一次「写进文件 ≠ 生效」。

## ★ 七、落地状态（**别照抄草案** —— 这段最重要）

这份 SOP 初稿很激进（"砍 AI 互请 / 直派不经中间层"）。
**实际落地时被改成了带条件的版本**，理由和判据都在这儿：

| 主张 | 实际裁决 |
|---|---|
| **砍 AI 互请 / 直派不经中间层** | ⚠️ **部分采纳** → 改成**条件性条款**：执行方能完全按单执行时，才不需要中间层 |
| **架构维护者退为维护者** | ✅ **采纳**（并扩了职责：+ 对外发布） |
| 路由看上下文 / 总线降为事实账 / 人是唯一裁决者 | ✅ **全部采纳** |

**为什么"直派"要加条件**：
执行方**当前还做不到**"完全按单执行" ——
真实事故：一张单派下去**没落地、也没人说**，还自称"已落地"，**瞒了 6 天**。
在这个状态下直接撤掉中间层 = **同时失去两层保护**。

**四条判据（同时满足，才算"可以直派"）**：

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | 接单有**收到确认** | 日志有对应条目 |
| 2 | 执行有**回执**（逐条对照 + 一行验证命令的**实际输出**） | 同上 |
| 3 | **不做也回**（显式写「未做 + 原因」） | 同上 |
| 4 | **连续 ≥3 次**全部满足 1–3，且**出单方独立复核通过** | 去机器**实跑** |

> **为什么要求"连续 ≥3 次"**：单次成功可能是运气；**能连续，才是能力**。
>
> **反过来也要防**：别因为"执行方看起来挺靠谱"就提前撤 ——
> 「看起来靠谱」不是判据，**「连续 3 次可验证的回执」才是**。

⇒ **撤中间层不再是豪赌**，而是一条**可量化、可复核、可随时回退**的路径。

## 八、和 wb-bot 怎么配合

| | **本件（SOP）** | **wb-bot** |
|---|---|---|
| 层 | **流程层** | **机制层** |
| 回答 | 活怎么派、谁该干什么 | 记录怎么不烂、通知怎么不丢、资源怎么不抢 |
| 形态 | 一份约定（文档） | 代码 + 模板 + 自测 |
| **迁移**（§六） | **定规矩**：接续必须带三样、搬完必须扫 | **给器具**：`wbb migrate render` / `audit` |
| **迁移门禁**（§6.6） | **定四律**：会变的不写死 / 权威只有一处 / 入口挂启动必读位 / 形状与接线分离 | **给判据**：[`tools/migrate_check.py`](https://github.com/WinterMK-byte/wb-bot/blob/main/tools/migrate_check.py) —— 前三条机械可查，接进 CI |

**配合方式**：SOP 决定"**下一步归谁**"，wb-bot 提供"**交接时不丢东西**"的器具。

> 同一个道理在**迁移**上也成立：
> SOP 说「执行层会被重建，接续必须带身份 / 在办事实 / 未闭口」，
> wb-bot 给出「怎么生成、怎么在搬完之后查到零命中」。**规矩与器具，缺一个都落不了地。**

## 九、最小落地清单

- [ ] 写一份施工单模板（目标 / 上下文 / 判据 / 路由 / 交付物）
- [ ] 建集中收件箱 + **贴脸投递**到对方工作区
- [ ] 总线纪律改成"事实账"（回执不是请示）
- [ ] 定"直派"的四条判据，**没达标就保留中间层**
- [ ] 每次派单走完：写单 → 投递 → 执行 → 回执 → 回读
- [ ] **给每条长期会话准备身份块**（短：只写身份 / 职责 / 边界）
- [ ] **重建前生成接续文本**，放进新会话「启动时真的会读到」的位置
- [ ] **重建后扫旧引用，跑到零命中**才算迁移收口

## 十、参与 / 反馈（**这份文档靠反例成长**）

> 本 SOP 每次大改都来自真实落地里的**反例** ——
> 0.2 那次（把"直派"改成带四条判据的条件性条款）就是被一个反例推动的：
> **一张单派下去没落地、也没人说，还自称"已完成"，瞒了 6 天。**

| 走哪扇门 | 什么时候用 |
|---|---|
| ★ **反例 · 哪条规矩不成立** | 你在真实场景里发现某一节有问题 —— **最欢迎** |
| **实战反馈** | 整份用下来，哪些成立、哪些不成立、代价是什么 |
| **想法** | 想加 / 想改的规矩（**必须带判据**） |
| **提问** | 「我这情况该怎么用」→ 走 Discussions |

**本仓库唯一的硬规矩：主张必须带判据。**

| ❌ 主张 | ✅ 可执行的规则 |
|---|---|
